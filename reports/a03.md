## 3. Decisions

**The evaluation plan: every stage measured separately (2026-11-06).** That way a wrong answer can be traced to the stage that broke.

| stage | metric | compared against |
|---|---|---|
| chunking | indirectly, through retrieval; plus chunk count and size, and IDs that stay the same after re-ingesting | the evidence ceiling (about 90%: captions aren't in the text) |
| retrieval | evidence recall@k (k = 1, 3, 5, 10) and MRR, per question type, within the question's paper | random k chunks; the paper's first k chunks |
| generation | answer F1 by answer type | closed-book (floor) and oracle (ceiling) from A0 |
| citations | ALCE citation recall and precision with the `NLI` judge; the share of uncited sentences | — |
| the judge | agreement with 50 sentence–citation pairs I label by hand | — |
| cost | latency and tokens per question | — |

Diagnostics:
* Split the dev questions by whether retrieval found the evidence. Wrong answers with the evidence found are reading failures; the rest are retrieval failures. That answers "how much of the gap to the oracle is retrieval vs reading".
* Shuffle the order of the retrieved chunks to see whether position matters ("Lost in the Middle").

Rules: design on the 200-question dev subset, and run test once per final configuration. Report bootstrap CIs, with paired comparisons since all systems answer the same questions. Compare retrievers at the same k and a similar token budget.

**Decision: how retrieval is scored against the gold evidence (2026-11-06).**
* **Main measure: coverage.** This is the share of the gold evidence's words that appear in the retrieved chunks, reported against the number of tokens retrieved. Noise and too little context are both real costs for the reader, so the comparison should be at a similar amount of text, not only at the same k. Precision (the share of retrieved text that is gold) is reported too, but it will always be low: annotators marked minimal evidence (usually one paragraph of about 60 words), and neighbouring paragraphs that also support the answer count as noise.
* **Hits, for recall@k and MRR, at three thresholds: 60%, 80% and 90%.** A retrieved chunk is a hit if it contains at least that share of a gold paragraph's words. Three thresholds instead of one show whether a conclusion depends on the threshold. The thresholds are fixed now, before any results. All three are reported side by side in the main tables, with no headline threshold. Where a single number is needed (for example, splitting questions into "retrieval found the evidence" and "it didn't" for the retrieval-vs-reading analysis), I use 80%: 90% asks for nearly the whole paragraph, and 60% lets in chunks that miss a lot of it.
* **Caption evidence counts as a miss.** About 10% of dev evidence is figure or table captions, which aren't in the text the retriever searches. Leaving them out would make the numbers look better than what the system can actually find. Keeping them in means every recall number has a ceiling of about 90%, which I state next to the results.
* **Several annotators: the best one counts.** Retrieval is scored against each annotator's evidence separately, and the highest score is kept. This is the same rule as A0's answer F1, which keeps the maximum over gold answers. I first considered using only the evidence common to all annotators, but on dev that set is empty for 31 questions: of 122 questions with two or more annotators who gave text evidence, 50 had identical evidence, 41 partly overlapping and 31 nothing in common. Those 31 would have been dropped or scored as misses, although each annotator's choice is valid evidence.

**Decision: a chunk's ID is source + paper ID + version + chunker config + index + a short content hash (2026-11-06).**
* The paper key (source, ID, version) is the same as the A1 event key, so a new arXiv version gets new chunk IDs.
* The chunker config (method, size, overlap, separators) decides where the cuts fall, so two chunkers never share IDs. This is the same idea as the A2 card key.
* The index keeps the order readable.
* The hash catches a change of text under the same index. For example, if a parser fix shifts text inside the same paper version, an index-only ID would silently point old citations at different text. With the hash, a stale citation becomes an ID that no longer exists, so it can be detected.

Tests to write once the chunker exists:
* chunking the same paper twice gives the same IDs;
* for the structure-aware chunker, changing one paragraph changes only the IDs of the chunks that contain it. For fixed-size windows every later window shifts, so every later ID changes too, and that is the expected behaviour;
* the same paper under two chunker configs gives disjoint IDs.

**Decision: both chunkers read the ingest `PaperModel` (2026-11-07).** The same chunker then serves the A1 library and the QASPER eval, so the demo searches with exactly what I measured. Checked on the 143 dev papers: `PaperModel` built by `qasper_source` has the same headings and paragraph strings as the eval adapter's `paper_text` for all 143. The only difference is that `qasper_source` drops blank paragraphs (135 on dev), and no gold evidence is blank.

**Decision: the fixed-size chunker uses blind windows of 256 tokens with a 64-token overlap (2026-11-06).**
* It cuts every 256 tokens wherever that falls, ignoring paragraph breaks. It is the baseline, so it must not respect structure. Otherwise the comparison with the structure-aware chunker would mostly measure a difference in size.
* The 64-token overlap is 25%. It makes a gold paragraph cut at a window boundary more likely to appear whole in one window, at the cost of about a third more chunks.
* The A2 `chunk_text` prefers to cut at `\n\n`, so it is closer to paragraph-packing and isn't this chunker as it stands.
* **Tokens are counted with the `EMBED` model's tokenizer** (Qwen3-Embedding-0.6B, the one A2's chunker already loads), so "256 tokens" means the same thing across the whole retrieval stack (2026-11-07).
* **The text it windows has the section headings inline**, each on its own line, as in A2's paper text (2026-11-07). Both chunkers then see exactly the same words, and the only difference between them is where they cut.

**Decision: every structure-aware chunk starts with its section heading (2026-11-06).** The reader then knows what the paragraph is about ("4.2 Results: ..."), and so do BM25 and the dense retriever.

**Decision: the structure-aware unit is whole paragraphs packed within one section, up to 256 tokens (2026-11-07).**
* A chunk never cuts a paragraph and never crosses a section boundary.
* 256 tokens is the same size as the fixed windows, so the comparison measures one thing, whether respecting structure helps, and not small chunks against big ones. One paragraph per chunk would match the gold evidence exactly, but it would change size and structure at once, and short paragraphs carry little context.
* A paragraph longer than 256 tokens (roughly the top 10%: dev p90 is 139 words) is split at sentence boundaries.
* TODO: whether the heading counts towards the 256 tokens.

**Decision: contextual retrieval comes later, as an add-on experiment (2026-11-06).** This is Anthropic's "Contextual Retrieval": an LLM writes a short note that places each chunk in its paper, and the note is indexed with the chunk. It is not a third chunker. It changes what a chunk carries, not where the cuts fall, so it is tested on top of the better chunker: no note, heading only, or LLM-written note. First the two required chunkers and the retrievers are built and measured, as the baseline. The note may be generated from the paper only, never from the question. Cost: one LLM call per chunk with the whole paper in the prompt. That makes it a candidate for the DeepSeek slot, where a repeated paper prefix is billed at the cache-hit rate.

**Decision: both chunkers use LangChain's splitters, as A2 did (2026-11-07).** I first had a hand-written version, then switched. The A2 setup can't be reused as it stands, so each chunker is configured to match the decisions above:
* **Fixed-size:** `split_text_on_tokens` with the `EMBED` tokenizer, 256 tokens per window, 64 overlap. This gives blind windows with exactly 64 tokens of overlap. A2's `RecursiveCharacterTextSplitter` would not be right here, because it prefers to cut at `\n\n`, then `\n`, then a space, so it respects structure and the baseline must not.
* **Structure-aware:** `RecursiveCharacterTextSplitter.from_huggingface_tokenizer`, run once per section so it never crosses a section boundary. It uses no overlap and tries separators in this order: paragraph break, sentence end, space, character. The sentence end is a regex that doesn't split after "et al.", "e.g.", "Fig." and the like, or a single initial. Each section gets 256 tokens minus its heading line minus a 4-token margin, and the heading is put back at the top of every chunk afterwards. The margin is needed because the splitter adds up the token counts of the pieces it joins, which can come out a little under the count of the joined text.

Compared on dev with the hand-written version (kept in the session scratchpad, not in the repo):
* The fixed windows are identical on all 143 papers, and no window contains a broken character.
* Structure-aware keeps exactly the same evidence paragraphs whole (453 of 484). It makes 179 more chunks (4,292 against 4,113): 79 because of the margin, and 100 because LangChain gives the leftover sentences of a split paragraph their own chunk instead of packing them with the next paragraph.

My calls inside the override (OVERRIDES.md, 2026-11-07):
* the heading counts towards the 256 tokens;
* the title is left out of both chunkers (no dev evidence is in it, and within one paper it would only take up a top-k slot);
* back matter is dropped in both with A2's `is_back_matter` (on dev it removes 73 sections, mostly acknowledgements, and none of the 499 evidence strings that match the body is in them);
* the hash is 8 hex characters of SHA-256 of the chunk text;
* the index runs over the whole paper.

A global index has a cost. An edit that changes how many chunks a section has shifts every later index, so every later ID changes as well. The "changing one paragraph" test uses an edit that keeps the chunk count. TODO: decide whether a per-section index (section number plus position) is worth it.

## 5. The retrievers (2026-11-07)

All three retrievers take the question, the paper's chunks and k, and return the top k as (chunk ID, score, rank). When scores tie, the paper's order decides, so runs are reproducible. A question that matches nothing returns the paper's first k chunks, which is one of the two baselines.

**BM25** (`copilot/retrieval/bm25.py`): rank_bm25's `BM25Okapi` with default settings (k1 = 1.5, b = 0.75), built per question over the paper's chunks.
* Words are lowercased runs of letters and digits: "BERT-base's F1" becomes `bert, base, s, f1`. No stemming and no stopword list.
* With only about 30 chunks, a word that is in more than half of them gets a negative IDF, which `BM25Okapi` replaces with a small floor. A paper's own topic words are often like that, so they count for almost nothing.
* Seen in a toy test: for "Which corpus is used for training?", the chunk "We train on the WMT14 corpus" lost to a chunk that only shares "is". With no stemming, "training" doesn't match "train". With no stopwords, "is" counts as much as "corpus". TODO: stemming and stopwords as an ablation on dev.

**Dense** (`copilot/retrieval/dense.py`): the `EMBED` slot (Qwen3-Embedding-0.6B) through sentence-transformers on `mps`, with an exact FAISS `IndexFlatIP` per paper.
* Vectors are normalized, so the inner product is cosine similarity. The index is exact, so the ranking has no approximate-search error in it.
* Chunks are embedded without an instruction. The question gets one in Qwen's format, `Instruct: <task>\nQuery:<question>`. The task sentence, chosen 2026-11-07 before any dense result: *"Given a question about research paper, retrieve relevant passages that help answer the question"*. It differs from Qwen's web-search default in two ways. It says the queries are questions about a research paper. And it asks for passages that *help* answer, not ones that *answer*: QASPER evidence often supports an answer without stating it, for example a results paragraph behind a yes/no question. If I change the sentence after seeing dev numbers, I report both versions.
* **float32, not the default bfloat16.** The weights are stored in bfloat16 and transformers loads them that way. The "normalized" vectors then came out 0.2–0.3% off unit length (norms 0.998–1.003 in a test). Forcing float32 gives exactly 1.
* **torch must be imported before faiss.** With `faiss` imported first, loading the model in float32 segfaulted on 5 of 5 tries, inside transformers' multi-threaded weight loading. Importing faiss first and loading in bfloat16 worked, and so did importing torch first in either precision. My guess is that the two libraries ship separate OpenMP runtimes and whichever loads first is the one used; I haven't confirmed it. The first full test run passed only because another test file had already imported torch. A test now imports `dense` in a fresh process, so test order can't hide it again.
* Each chunk is embedded once and stored by model name + snapshot revision + dtype + chunk ID (`evals/cache/embeddings/`). The chunk ID ends in a hash of the text, so a stored vector can't belong to different text.
* **Embedding time (measured 2026-11-07, M3 Pro, `mps`, float32, batch 32):**
  * The 4,292 structure-aware dev chunks took 339 s, or 79 ms per chunk.
  * The 3,609 fixed-size chunks were already in the store from an earlier run that I stopped, so their time wasn't measured. They are longer (all 256 tokens, against a median of 172), so they probably take more per chunk. TODO: measure it with a fresh store if the number is needed.
  * Read back from the store, all 7,901 dev chunks take under 0.1 s.

**Hybrid** (`copilot/retrieval/hybrid.py`, 2026-11-07): reciprocal rank fusion (Cormack et al., 2009). I wrote the core; the plumbing around it was written for me under an override.
* A chunk scores 1 / (60 + rank) for each list it is in, and 0 for a list it isn't in. Only ranks are used, because BM25 scores (about 7) and cosine scores (about 0.6) are on different scales and can't be added.
* k = 60 is the paper's value, fixed before any result. A larger k flattens the gap between ranks, so two lists agreeing counts for more than one list's first place.
* Worked example (a unit test): BM25 ranks A, B, C and dense ranks B, D, A. The fused order is B (0.0325), A (0.0323), D (0.0161), C (0.0159). B wins because both lists put it near the top, and a chunk that only one list found comes after any chunk that both found.
* Ties keep the order the chunks were first seen in: the dense list's order, then BM25-only chunks in BM25's order.
* **Decision: each retriever hands over its top 50, and only the fused list is cut at k (2026-11-07).**
  * I first proposed cutting each input list at the same k as the output. But then, at k = 1, hybrid always returns dense's top chunk: the two single-item lists either agree, or tie at 1/61 each, and ties go to dense. Hybrid@1 would equal dense@1 by construction.
  * With a fixed depth, hybrid@1 is the chunk the two rankings agree on most, which is what that row should measure.
  * 50 is the whole paper for nearly every question. On dev, only 5 of 200 questions are on a paper with more than 50 fixed-size chunks, and 11 of 200 with more than 50 structure-aware ones. For those, chunks below 50th get nothing from that list.
* Planned check: compare the fused scores with a library's RRF on dev. They should match exactly at the same k and depth.

## 6. Retrieval on dev (first run, 2026-11-07)

Run `20261107-135633_a3_retrieval_dev` (`uv run python -m evals.a3_retrieval --subset dev`), on an uncommitted working tree.
* **Questions:** 185 of the 200 dev questions have gold text evidence. The other 15 are unanswerable or have no evidence, and are left out.
* **Run time:** the whole run took 41 s from stored embeddings. Per question, BM25 takes about 1 ms and dense about 40 ms.

**How the metric matches words** (my calls inside the override):
* Words are lowercased letters and digits. A gold word counts as found only inside a run of at least 5 consecutive gold words that the chunk also has.
* Checked on dev with the structure-aware chunks: every chunk that really contains a gold paragraph is fully found (461 of 461). With a 5-word minimum, 4.9% of the other chunks match anything at all, and the mean false share is 0.5% of a paragraph. A 3-word minimum would let in 30% of chunks, and 8 words gains little over 5.
* MRR is over the top 10.
* The random baseline is the mean of 20 seeded draws per question.

**Findings** (paired bootstrap over the same 185 questions, 10,000 resamples):
* **Dense beats BM25 under both chunkers, at every k and every threshold I checked.** For example, structure-aware R@5@80 is +0.157 [+0.085, +0.232], better on 58 questions and worse on 23.
* **Hybrid doesn't beat dense.** Dense is slightly ahead everywhere (+0.008 to +0.023), but no difference is outside its CI. Hybrid does beat BM25 clearly. So on this subset, RRF with an equal-weight BM25 list adds nothing to dense. BM25 is weak enough that it dilutes the fusion more than it helps.
* **Structure-aware beats fixed windows at the 80% threshold for dense and hybrid:** R@1 +0.065 [+0.006, +0.126], R@5 +0.081 [+0.014, +0.149], MRR +0.067 [+0.012, +0.123]. At R@10 the difference shrinks and its CI includes 0.
* **That advantage depends on the threshold.** At 60%, structure minus fixed for dense R@5 is +0.009 [−0.048, +0.067]. Fixed windows usually hold most of a gold paragraph but cut its ends. A strict threshold counts that as a miss, and a loose one doesn't. This is why the three thresholds are reported side by side.
* **At the same number of tokens, structure-aware gives the reader more evidence.** Dense structure-aware at k = 5 covers 0.653 of the gold words with 783 tokens. Fixed windows need about 1,244 tokens for the same coverage (0.648 at k = 5), and at a similar 745 tokens (k = 3) they cover 0.543.
* **"The paper's first k chunks" is worse than random.** The first chunk is always the abstract, and no dev evidence is in the abstract. Structure-aware R@1 for first k is 0.000.
* **By question type** (R@5@80, structure-aware, BM25 / dense / hybrid): extractive (n = 129) 0.500 / 0.688 / 0.642, abstractive (n = 34) 0.364 / 0.514 / 0.511, yes/no (n = 22) 0.424 / 0.409 / 0.492. On yes/no, hybrid is ahead and BM25 is level with dense. With n = 22 I don't draw a conclusion from that. TODO: paired CIs per type.

  * The reason to carry hybrid forward: on retrieval alone it is level with dense, not worse beyond noise. Retrieval recall isn't the same thing as answer quality, so the reader may use the two sets of chunks differently.
  * Fixed windows and BM25 stay as measured comparisons in §6.
  * Rule: the choice between dense and hybrid is made on dev and written here before test is run. If both go to test, both are reported, and neither is picked as the headline because of its test number.
* **Decision (2026-11-07): the grounded-generation setup.**
  * **Reader: MEDIUM (qwen3:8b) with A0's oracle settings** (temperature 0.6, thinking on, max_tokens 4,000). Then answer F1 lines up directly with A0's closed-book and oracle numbers.
  * **k = 5 and k = 10**, both run. Structure-aware k = 5 is about 780 tokens of chunks (dense R@5@80 = 0.623). k = 10 is about 1,600 tokens (R@10@80 = 0.764).

  * **The 8,192-token box, checked 2026-11-07** with the EMBED tokenizer (Qwen3's vocabulary, so close to the reader's count):

* **Decision (2026-11-07): the answer prompt, `copilot/answer/prompts/grounded_v1.txt`.** It is my A0 oracle prompt with these changes:
  * **Every answer is cited,** short ones included, with [n] after each claim: "News Articles [2], Twitter [4]", "yes [1]". I first wrote "for abstract answers" only, then changed it. The citation eval checks every answer, and 151 of the 185 answerable dev questions are extractive or yes/no, so they would all have counted as uncited. The model also can't tell which type of question it has.
  * **Unanswerable:** "When the given evidence is not sufficient to answer the question, do not create false claims to answer it. Just say "Unanswerable", with no citation." This is stricter than A0, where the oracle already answered Unanswerable on 17–18% of answerable questions. TODO: report "Unanswerable on answerable questions" as its own number in every run.
  * **"Some passages may not be relevant to the question".** The passages are now retrieved, not gold, so several of the 5 or 10 will be off-topic.
  * **The three few-shot answers now carry citations,** because a small model copies the examples more than it follows the instructions. The examples come from train papers; I checked that none is in dev or test.
  * **Length:** 1,627 tokens. The k = 10 worst case is now about 7,770 of 8,192 tokens.
  * **Answer F1 is scored with the [n] markers removed,** since they would count as wrong words against the gold answer. Citations are scored separately.
