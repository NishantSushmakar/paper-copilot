## 1. What SciREX measures (read 2026-11-01)

Three ideas from the SciREX paper (Jain et al., 2020) shape the whole assignment:

* **A mention** is one place in the text where an entity's name appears. "SQuAD" written 14 times is 14 mentions.
* **A cluster** groups the mentions that refer to the same real-world entity: "SQuAD", "SQuAD 1.1" and "the Stanford Question Answering Dataset" can all sit in one cluster.
* **A cluster is salient** if it takes part in one of the paper's results, the (dataset, metric, task, method) tuple a reported score belongs to. A dataset mentioned once in related work is not salient.

My eval compares predictions against **salient clusters**. A real entity that appears in the paper but isn't salient (CoNLL-2003 named only in related work) counts as a **false positive**. So the prompt has to ask for what the paper uses for its results, not for everything it mentions.

**Type names.** SciREX's four types are `Task`, `Method`, `Metric` and `Material`. There is no `Dataset` type. My card's `datasets` field maps to SciREX `Material`. Searching the data for "Dataset" would find nothing and give a recall of 0 that looks like a model failure.

## 2. The `PaperCard` schema: decisions

### Entities carry several names

The paper is longer than the context, so extraction runs per chunk and each chunk produces its own card. Chunk 2 may write "Stanford Question Answering Dataset (SQuAD)", and chunk 7 "SQuAD v1.1". If a card kept one name per entity, the merge step would only see two bare strings and lose the fact that chunk 2 saw both forms together.

* **Each entity is one entry with a list of names.** SQuAD is one dataset with the names "Stanford Question Answering Dataset" and "SQuAD", not two datasets.
* **The eval scores one name per entity.** This gives at most one true positive per predicted entity, and a model can't inflate its score by padding an entity with loose names like "the dataset".
* **That name is the most frequent one.** The merge step counts how many chunk cards list each exact name (after normalization), and the most frequent one is used for scoring. A noisy one-off phrase such as "the SQuAD benchmark we use for all experiments" rarely repeats, so frequency filters it out. The abbreviation a paper uses throughout is also the form most likely to be among SciREX's mentions.
* **Ties go to the longest name.** A paper that fits in one chunk has every name at count 1.
* **Exact names, not substrings.** Substring counting would merge different entities: "SQuAD" is inside "SQuAD 2.0", and "BERT" is inside "RoBERTa".
* **The card stores no counts.** The merge step counts across cards by itself.

Known trade-off: scoring one name loses recall when the chosen name isn't among a cluster's mentions but another of the entity's names is. An alternative scoring rule ("any name may match, at most once per entity, generic names excluded") is a planned ablation on dev. ### Result values: raw text plus a parsed number

* **Two fields.** One keeps the value exactly as the paper writes it (`85.3%`, `85.3 ± 0.2`, `—`). The other holds the parsed number. Keeping the raw text means nothing is lost (the ± part, the paper's own formatting), and A9 can still find the exact string in the source.
* **My code does the parsing, not the model.** A parser is deterministic, free and testable. Asking the model to convert costs a call and can go wrong.
* **The parsed number may be empty.** When a table shows `—`, the paper has no number. If I required one, S2 would send "value must be a number" back to the model, and the model's easiest way out is to invent a score that then looks exactly like a real one. An empty value is not 0.
* **Telling "no value" from junk.** Both `—` and `high` fail to parse. The validator keeps `—` (the paper has no number) and rejects `high` (the model gave junk). I use a list of the ways papers write "no value" (`—`, `–`, `-`, `N/A`, `n.a.` and so on). The list will be incomplete at first, so I log every rejected raw string, read them after a dev run, and add any real "no value" markers. The list grows from evidence, never from test data.
* **What counts as a value: one number, plus optionally `%` and/or `± number`. Nothing else.** `85.3`, `85.3%`, `85.3 ± 0.2` and `85.3 ± 0.2%` all parse to 85.3 (the `%` may come before or after the spread). A trailing dot is accepted (`85.` → 85.0): the LLM most likely copied the number from the end of a sentence, and rejecting it would cost a retry over a full stop. The spread stays in the raw text, since nothing in A2 uses it. `85.3 vs 90.1` is rejected: it's two results squeezed into one, and only the model knows which method got which score. `85.3 (Table 2)` is rejected too: the LLM should write only the value. I chose an allowed-extras list over "take the first number": the first-number rule would accept `85.3 vs 90.1` as 85.3 (silently dropping a result) and `top-5` as 5. Consequences: the prompt and the S2 error message both have to state the allowed format, and since S1 has no retry, one bad value fails the whole card. I log which field caused each card failure. If result values cause a large share of S1 failures, that's a reason to drop just the bad result instead. Thousands commas are accepted (`1,234` → 1234), and so is the Unicode minus `−` that arXiv HTML uses (`−1.2` → -1.2). Both are normalized before matching. A comma is removed only when it sits in a thousands position, i.e. followed by exactly three digits. `12,34` could be a decimal comma meaning 12.34, and deleting every comma would silently store a value 100× too big, so it's rejected and the model rewrites it. I considered asking the LLM to write numbers in decimal format instead, but that breaks two earlier decisions: the raw value would no longer be the paper's text, and the conversion would move back from my code to the model. `-`, `–` and `n/a` join the "no value" markers, compared ignoring case. A raw value the LLM wrote as a number (`85.3` without quotes) is converted to the string `"85.3"` silently, then parsed as usual. That's a logged silent fix.
* **Scale: stored as written, not normalized.** The `%` sign alone can't tell me whether a number is a percentage: an F1 column may show `85.3` with no sign, and `BLEU 34.2` isn't a percentage at all. A correct conversion has to know the metric. The A2 eval scores entities, not values, so nothing in A2 needs values on one scale. I store the number as the paper writes it (`85.3%` → 85.3, `0.853` → 0.853) and leave the metric-aware conversion until something compares values across papers.

### Validators: fix or reject

The test for each mistake: **does fixing it need the model's knowledge, or only a mechanical rule?** A mechanical fix is free. A rejection costs a full model call in S2 and fails the whole card in S1, which has no retry.

| model mistake | decision | why |
|---|---|---|
| duplicate names (`"BERT"` / `"bert"`) | fix silently | a mechanical rule handles it |
| value `"high"` | reject (S2 retries) | no rule can recover the number; only the model, rereading the paper, can |
| empty string in a list | drop silently | it holds no information, so a retry would recover nothing |
| an entity whose names are all empty (`["", " "]`) | drop the entity silently, in `PaperCardModel` | the same mistake as one empty name, only bigger: a retry recovers nothing. It has to happen in the card, because an entity can't remove itself from the card's list, and rejecting inside the entity would fail the whole card |
| a bare string or a number instead of a list of names | currently rejected by Pydantic's type check (TODO: confirm, or fix silently) | a shape mistake, so it goes back to the model |
| the same entity listed twice in one card (`["SQuAD"]` and `["squad"]` as two entities) | left to the merge step | the merge already has to match entities across chunks, and this is the same job; one place for that logic instead of two. Every paper goes through the merge, even one that fits in a single chunk, or these duplicates would survive |
| `code_url` that isn't a valid http(s) URL (`"Code will be released upon publication"`, `ftp://…`) | reject | it isn't a link. "No link" has exactly one value, `None`, and empty strings become `None`, so later code asking "does this paper have code?" checks one thing. Cost: in S1 a bad code URL fails the whole card, so I count how many cards each strategy loses this way. The error message tells the model what to write instead: an http(s) URL, or null if the paper gives no link. A link with no scheme at all (`github.com/foo/bar`) gets `https://` added silently, since that's a mechanical fix. One with the wrong scheme (`ftp://`) is still rejected, and so is plain text, which stays invalid even with `https://` in front. `https://` is added only when the host has a dot, because `none` and `N/A` otherwise became `https://none/` and `https://n/A`. "No link" markers (`none`, `n/a`, `n.a.`, `na`, `null`, `tbd`) become `None`. This list is kept separate from the result-value markers on purpose: `-` and `—` are how a table cell says "no value", while `none` and `TBD` are how an LLM says "no link". Known gaps (`https://none` still passes) get fixed from logged dev-run outputs, not by guessing more rules |
| a result whose `dataset`, `metric` or `method` is empty or only spaces | reject (S2 retries), in `ResultModel` | a result like `{dataset: "", metric: "F1", method: "BERT", raw_value: "85.3"}` holds a real number the model found. Only the model, rereading the chunk, can say which dataset it belongs to, and dropping would silently throw that score away. I first chose to drop and switched to reject for this reason. Cost: in S1, which has no retry, one such result fails the whole card, the same cost I accepted for result values. It's counted through the per-field card-failure log. The error message names the empty field and says every result needs a dataset, metric and method. This never needs handling after the merge: the merge only combines chunk results that already passed this check, and it's my code rather than a model call, so there is nothing to retry. An empty name there would be a merge bug, caught by a test |
| a list left empty | allowed, in chunk cards and final cards | a chunk (say, related work) may honestly hold no methods, and some papers have no entity of a given type. But an empty final card can't show whether the paper has none or the model missed them, so I count empty fields per strategy and model as a warning sign |
| result's dataset, metric or method missing from `datasets`, `metrics` or `methods` | add it to the matching list silently | the model used the entity, so most likely it only forgot to list it. This happens when the model reads "datasets" as "datasets the paper introduces", or loses track over a long JSON answer. It matters because the eval scores the entity lists, not `results`, so an entity named only inside a result would be a lost true positive. The check covers all three types a result names. `tasks` is not checked because results carry no task (TODO: decide whether they should). "Already listed" ignores case and surrounding whitespace (`"squad"` and `" SQuAD "` both match `["SQuAD"]`), and a match on any of an entity's names counts (`"SQuAD"` matches `["Stanford Question Answering Dataset", "SQuAD"]`), so nothing gets added twice. The strip happens once, in `ResultModel`, so the card stores `"SQuAD"`, not `" SQuAD "`. If each comparison stripped instead, every later comparison (the cross-check, the merge, the eval, A9) would have to remember to do it, and forgetting once brings back `" SQuAD " ≠ "SQuAD"` as a silent bug. This is the same choice `EntityModel` makes for names. A missing entity is added once, even if several results name it, and existing duplicates in a list are left to the merge step. Open: I wanted `"SQuAD v1.1"` vs `["SQuAD"]` to count as listed too, but that needs a rule beyond exact names, and the obvious substring rule would also call `"RoBERTa"` listed under `["BERT"]` and drop a real method. It's a trade-off between a duplicate FP (if SciREX clusters both spellings together) and a lost TP. ### Chunker interface (decided 2026-11-02)

* **One chunker for both sources.** It's built with the A1 papers in mind, but SciREX goes through the same chunker. Otherwise the SciREX F1 would describe a different system from the one that makes the A1 cards. Plain text split on whitespace works for both: no SciREX word in train or dev contains whitespace, so joining SciREX words with spaces and splitting again gives back exactly the original words.
* **What goes into the A1 text:** the abstract (it often names the task, dataset, method and code link) and the section headings. SciREX's words already contain both (`section : Related Work`), so the two sources look alike. The title is included too, as SciREX's first section appears to be the title.
* **Each chunk keeps its position: its chunk number and its start and end word offsets in the whole paper.** The number gives the order. The offsets say where the chunk sits, so the merge can tell whether a result found in two cards lies in their shared words, and A9 can trace a value back to its place in the paper. SciREX's gold mentions are word offsets in the same word list, so I can also check which gold entities actually occur in a given chunk. That separates "the model missed it" from "it wasn't in the chunk".
* **A paper shorter than one chunk** becomes one chunk holding the whole text. **A paper slightly over the budget** gets a second, overlapping chunk, even if most of it repeats the first; the merge handles the duplicates. I considered equal-size chunks instead, which give the same number of calls with no scrap chunk, and chose the simpler rule.
* **Built on LangChain's `RecursiveCharacterTextSplitter`, not written from scratch.** Splitting is a standard component, and my job as an AI engineer is to choose and configure it. Configuration that keeps the decisions above:
  * `from_huggingface_tokenizer` with the Qwen3 tokenizer, not `from_tiktoken_encoder`. tiktoken is OpenAI's tokenizer, and the 52-token budget margin depends on Qwen counts.
  * Separators chosen so that SciREX (no newlines) and A1 text (newlines) are chunked alike.
  * Character start offsets from the splitter, converted to word offsets.
  * TODO: decide which exact-fill tests (last word that fits, as many overlap words as fit) still matter, since the splitter sums piece lengths and may stop slightly short. ≤ 2,600 tokens stays strict.
* **Structure first: SciREX is converted to look like an A1 paper before chunking.** Sections are separated by a blank line in both sources. A1 paragraphs are separated by `\n`. SciREX sentences are joined with plain spaces, not `". "`: SciREX already stores each full stop as its own word, so adding `". "` would insert extra words and shift every offset. Because `text.split()` treats newlines like spaces, the SciREX word list, and so its alignment with the gold mention offsets, is unchanged. With separators `["\n\n", "\n", " ", ""]`, the splitter packs whole sections into a chunk, cuts inside a section (paragraphs for A1, words for SciREX) only when the section alone is too big, and cuts inside a word only as a last resort. This replaces "a chunk ends exactly where 2,600 tokens run out": chunks now often stop short at a section break, which costs a few more calls but means chunks usually start at a heading. **Overlap only where a cut lands inside a section.** LangChain builds overlap from whole pieces at the current level, and a section is usually longer than 100 tokens. A section break never cuts a sentence, so it needs no overlap. This answers the earlier "every boundary or only inside split sections" question.
* **Two LangChain pitfalls my tests caught** (checked with a throwaway reference implementation, not my chunker):
  * `add_start_index=True` breaks whenever chunks overlap. LangChain computes `offset = previous_start + previous_chunk_len − chunk_overlap` and then `text.find(chunk, offset)`. It subtracts a token count (100) from a character position, but 100 tokens is roughly 400 characters, so the search starts past the real start and returns `-1`. On a test text, chunk 2's true start was character 235, and LangChain reported -1. So chunk positions must be found by my own code, and the word offsets are checked by the tests rather than trusted.
  * Token counts are summed per piece, so a joined chunk can come out slightly longer than the limit (121 against 120 in a synthetic word-level test). On 60 SciREX train papers at 2,600/100 with section-first splitting: 194 chunks (median 3 per paper, max 9), chunk size median 2,343 tokens and max 2,600, **0 chunks over 2,600**, and all word offsets correct. The ≤ 2,600 test stays strict. Worst case, on 100 train papers joined with spaces only (no section breaks, so every cut is between words): 11 of 311 chunks were over 2,600, each by exactly **1 token**. **Decision: ask the splitter for slightly less than the limit** (a safety margin below `chunk_size`), and keep the ≤ `chunk_size` check after splitting. The margin is `min(8, max(1, chunk_size // 100))`: 8 tokens at 2,600 and 1 at 120, several times the measured 1-token overshoot at a cost of 0.3% of a chunk.

**The chunker as built** (`copilot/cards/chunking.py`, 8/8 tests passing). It asks LangChain for `chunk_size − margin` with separators `["\n\n", "\n", " ", ""]`. It finds each chunk itself by searching the text from just after the previous chunk's start, which always finds the right copy because chunks only move forward and overlap backwards. It computes word offsets from those character positions and logs any chunk that starts or ends inside a word. A chunk still over the limit is re-split (`split_oversized`), and a chunk that can't be located is logged and skipped. Measured on my code:
* SciREX train, section-first text: 306 papers → 968 chunks in 19 s, median 3 per paper (max 9), chunk size median 2,296 and max 2,592 tokens. Offsets and word coverage were correct on all 306 papers, with no mid-word warnings.
* The longest A1 paper: 50,987 tokens → 28 chunks in 0.5 s, offsets correct.

### Merge (decisions so far, 2026-11-02)

* **When are entities from different chunk cards the same entity? Main rule: they share a name** (compared ignoring case). Linking is transitive: `["Stanford Question Answering Dataset", "SQuAD"]`, `["SQuAD"]` and `["SQuAD", "SQuAD v1.1"]` all become one entity through "SQuAD". Risk: one sloppy card glues unrelated things together for the whole paper. For example, the 4B model's `["FRRN A", "FRRN B", "ResNet"]` would make FRRN and ResNet one entity, and one of them drops out of scoring.
* **Dev ablation: a stricter rule, where two different names are joined only if at least 2 chunk cards put them in the same entity.** Identical names are always the same entity. This blocks a single sloppy card. The cost: abbreviations are usually defined once, in one chunk ("Stanford Question Answering Dataset (SQuAD)"), so they often stay unjoined and the long name becomes a second prediction against the same gold cluster. I considered and rejected "keep an entity only if at least 2 chunks mention it": it's a different idea (a precision filter), it drops real entities that appear in only one chunk, and it would empty every single-chunk paper. Both rules run on the same dev cards, and their precision and recall answer A2's written question about how the merge strategy affects precision vs recall. TODO: what the strict rule does for a single-chunk paper (probably trust that card's own groupings).
* **The merged card is still a `PaperCardModel`, and every value is kept.** When chunks report different numbers for the same result (65.7 vs 71.8, say validation vs test), each value stays as its own row. Exact repeats, such as from chunk overlap, collapse into one. I considered a merged-result model holding a list of values with the chunk each came from. It would save A9 a lookup, but nothing in A2 needs provenance, so the simpler shape wins for now.
* **Two results are the same result when their dataset, metric and method resolve to the same merged entities.** So `"cityscapes"` / `"IoU"` matches `"Cityscapes"` / `"mean IoU"` if the merge grouped those names. **Two values are the same when their `parsed_value` is equal** (`"65.7%"` = `"65.7 %"`). Two "no value" markers, both parsed to None, also collapse. TODO: confirm that merged results are rewritten to the merged entity's scoring name, so results and entity lists agree.
* **`code_url`: the most frequent non-null URL across chunk cards.** Ties go to the earliest chunk, and any disagreement is logged. Nulls are ignored because most chunks honestly have no link. This is the case from §5: a real link in one chunk, a placeholder in another.
* **Failed chunks: merge the valid chunk cards and record coverage** (valid chunks out of total). One cut-off chunk doesn't lose the whole paper, and the eval can report results with and without incomplete papers.
* **Coverage lives in a small wrapper, `MergedPaper`:** the paper, strategy, slot, prompt version, merge rule, chunks total and valid, the merged card, chunk failures (chunk, status, failed fields), every chunk's silent fixes, and the model calls, tokens and latency summed per paper. That's one JSONL row per paper, next to the per-chunk rows.
* **The scoring name comes first in `names`.** The card stores no counts, so the order carries the decision. The eval reads `names[0]`, and merged results are rewritten to the scoring names, so results and entity lists always agree.
* **As built** (`copilot/cards/merge.py`, written under an override; 18 tests, 155 in total). Names are compared ignoring case and runs of whitespace. Entities are joined with union-find, a connected-components structure where names linked through shared names end up in one group. Under `agree2`, a pair of different names is joined only if at least 2 chunk cards put them in one entity, and a single-chunk paper trusts its card. A merged entity's display spelling is the paper's most common spelling of each name.

## 6. SciREX eval design (decided 2026-11-02, from train only)

**What the gold looks like** (train, 306 papers, 2,424 salient clusters):

| | count |
|---|---|
| clusters with **no mentions at all** | **691 (29%)** |
| …of those, part of a result relation | 638 |
| …combined names (`X___Y`, e.g. "V-Net + Dice loss") | 64 |
| …whose name appears verbatim in the text | 61 |
| cluster type from relation role vs from NER tags | agree 1,567, disagree 4 |
| clusters with no type from either | 53 |
| salient clusters per paper (median) | 1 of each type (means: Material 2.70, Method 1.46, Metric 1.84, Task 1.22) |
| distinct mention strings per cluster | median 2, max 33 |

The mention-less clusters are mostly entities that only appeared in the results tables SciREX dropped: column headers and row labels such as `Frame (fps)`, `BLEU-4`, `Daily Mail`. For example, train doc 1's result `V-Net___Dice-based_loss … 0.869` has no mentions, and 0.869 appears nowhere in the text. Mentions keep SciREX's tokenization, with spaces around every hyphen and bracket (`V - Net`, `” PROMISE2012 ”`).

**Decisions:**

* **Mention-less clusters stay in the gold.** It's the honest evaluation: they are salient entities, and a text-only system misses them. The cost is a recall ceiling of roughly 71% for any system, so every recall number is reported next to its ceiling (the share of gold clusters per type that have at least one mention). Optional: a "text-visible recall" column that ignores mention-less clusters.
* **Cluster type:** the relation role first (Material → my `datasets`), then the majority NER tag of its mentions. The two agree 1,567 to 4. Clusters with no type from either are dropped and counted.
* **Normalization before matching:** casefold, then keep only letters and digits, so `V - Net` and `V-Net` become `vnet`, and `PROMISE 2012` and `PROMISE2012` become `promise2012`. Digits must stay, or `BLEU-1` and `BLEU-4` would both become `bleu` and `SQuAD v1.1` would equal `SQuAD v2.0`.
* **Exact match after normalization** is the main number. A prediction is correct if its normalized scoring name (`names[0]`) equals the normalized form of any mention of a gold cluster of the same type. Fuzzy matching (similarity ≥ 0.95, e.g. `difflib` ratio) is a later ablation, scored on the same stored cards with no extra model calls. At 0.95 it mostly forgives plurals and one-letter typos in long names (`…neuralnetwork` vs `…neuralnetworks` ≈ 0.98), while `bleu4` vs `bleu1` (0.80) and `resnet50` vs `resnet18` (0.75) stay different. The any-name scoring ablation from §2 is also scored this way.
* **One-to-one matching:** each gold cluster can be found at most once, and each prediction can find at most one cluster. A second prediction for an already-found cluster is a false positive (unmerged `SQuAD` and `Stanford Question Answering Dataset` count as 1 TP + 1 FP), so precision rewards a merge that joins aliases. When a prediction could match several clusters, a maximum matching is used, so the count doesn't depend on the order of predictions.
* **Micro-averaged** precision, recall and F1 per field: TP, FP and FN are summed over papers, then computed once. Bootstrap CIs resample papers and recompute the sums (the A0 bootstrap: 10,000 resamples, 2.5th/97.5th percentiles, seed 42).
* **A paper with no card** (a crash, or no valid chunk) is scored as an empty card: all its gold clusters are false negatives. Every strategy is scored on the same 66 papers, so none can look better by failing on hard papers.

**As built** (written under an override): `evals/adapters/scirex.py` (doc → text + typed gold clusters), `evals/metrics/scirex.py` (normalization, one-to-one maximum matching, micro P/R/F1, the recall ceiling, paper-level bootstrap CIs), and `evals/a2_scirex.py` (the runner; it writes `chunks.jsonl`, `papers.jsonl` and `summary.json`, with first-attempt and final validity, retries, a first-failure → outcome breakdown for "which errors did retries fix", latency and provenance). 21 tests (176 in total). On train, the adapter gives 2,371 typed clusters (824 datasets, 608 methods, 565 metrics, 374 tasks), 53 untyped and dropped, and 638 mention-less, so the recall ceiling is **73.1%**. The text reproduces SciREX's word list exactly.

**Smoke test** (train doc 0, SMALL, all three strategies, 5.3 min; one paper and one sample, so this checks the plumbing, not the scores): every chunk was valid for all strategies; overall F1 was 0.333 (S1, S2) and 0.316 (S3); the paper's recall ceiling was 75%. A manual check against the gold confirmed the metric behaves as designed, and showed two leads for after the dev run:
* **Abbreviation inside the name.** The scoring name `Full-Resolution Residual Networks (FRRNs)` normalizes to `…networksfrrns`, which matches neither `fullresolutionresidualnetworks` nor `frrn`, so methods F1 was 0. Fix candidates: the prompt asks for the abbreviation as its own name, or normalization drops a trailing `(…)`. The second is an eval change and would apply to every run.
* **Synonyms the merge can't join.** `semantic image segmentation`, `segmentation` and `semantic segmentation` came out as three entities. All three are mentions of one gold cluster, so one-to-one matching scores 1 TP + 2 FP. They share no name, so the share-a-name merge can't link them.

**Compute budget** (chunk counts from my chunker; latencies from §5, so rough): dev is 66 papers, **203 chunks**; test is 66 papers, **225 chunks**. Per slot, S1 and S3 are each one call per chunk, and S2 adds only its retries, since attempt 1 is S1's cached call.
