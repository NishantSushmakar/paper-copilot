## 4. Design decisions

### The LLM cache key with tools (2026-11-09)

* **Decision: every offered tool's name, description and parameters schema goes into the cache key.** The rule stays the one the key already follows: everything that can change the reply. The schema is the full JSON the model receives (types, argument descriptions, enums, defaults, `required`).
* **Why the description too:** I first thought the name carried the meaning and the description could stay out. A two-line test showed otherwise. With qwen3:4b, temperature 0, one tool `lookup(query)`, and only the description changed ("Look up facts about any topic." vs "Look up a paper in the user's research library by title. Not for general knowledge."):
  * "Who wrote Hamlet?": a direct answer with A, a different text with B;
  * "What year was the transformer paper published?": both call the tool, with `query` = the whole question (A) vs `'transformer paper'` (B).
  * So the model reads the description as part of the prompt. Leaving it out of the key would make a reworded description silently replay the old replies from the cache, and a description fix would measure as "no change".
* **Output side:** the tool calls a reply makes are stored in the cached value. `LLMResponse` held only text, so a cache hit on a tool-call reply would have lost the calls. It now has `tool_calls` (name, args, id), defaulting to an empty list so older entries still load.
* **Decision (agent's call, 2026-11-10): a call without tools hashes exactly as before.** `tools` and `tool_choice` enter the key only when set, and plain `{"role", "content"}` messages come out of the normalisation unchanged, so the A1–A3 caches stay valid. Also `tool_choice` without tools raises, and a tool result whose call isn't in the conversation raises.
* **Decision: the tool's Python body stays out of the key.** One agent step is two model calls. The first (question + tool definitions → "call search(...)") contains nothing the body produces, so fixing the body can't change its reply, and its cached reply stays valid. The body's effect reaches the model only as the tool result in the *next* call's messages, and messages are already in the key, so that call misses the cache and gets a fresh reply by itself. Putting the body in the key would only discard valid first-call replies on every code change.
* **Found 2026-11-09: turn-2 messages break the key.** From the second agent call on, `messages` holds LangChain objects (`AIMessage` with tool calls, `ToolMessage`), and `json.dumps` raises `TypeError: Object of type HumanMessage is not JSON serializable`. Also, ChatOllama gives every tool call a fresh random id (checked: the same call with the same arguments got two different UUIDs in two runs), so serialising the objects as they are would put a random value in the key, and every call after the first would miss the cache on replay.
* **Decision: a message enters the key as its role, its text content and, for an assistant message, each tool call's name and arguments.** Text alone isn't enough: two runs whose assistant called `search(query="SecAlign")` vs `lookup(title=...)` both have empty assistant text, and "Paris" from the user is not "Paris" returned by a tool.
* **Decision: random tool-call ids are renamed by position before keying.** The id links a tool result to its call, which matters with parallel calls, so it can't just be dropped. In the key, the first call in the conversation becomes call 1, the next call 2, and so on, and each tool result points to the renamed id of its call. The same step run twice gets the same key despite new UUIDs; results that come back in a different order still give a different key, which is right, because the model reads messages in order.
* **Decision: the tool list goes into the key in the order given, not sorted.** Ollama pastes the definitions into the prompt one after another, so `[search, lookup]` and `[lookup, search]` are different prompt text and can give different replies. (`sort_keys=True` sorts keys inside dictionaries but never reorders lists.)
* **Decision: `tool_choice` raises an error on Ollama slots, and goes into the key where the provider honours it.** It's a separate setting, not part of any tool definition, so the description being in the key doesn't cover it. LangChain's `ChatOllama.bind_tools` documents it as "currently ignored as it is not supported by Ollama". A setting that is silently ignored is worse than none: an agent passing `tool_choice="required"` would look forced while the model can still answer in plain text. The OpenAI-compatible path (vLLM, hosted models) supports it.
  * Consequence for A5: "the model must act" or "must end with `final_answer`" can't come from `tool_choice` on Ollama. It has to come from the prompt and the loop's own checks.

### The registry: first principle (2026-11-09)

* **A step that must always happen is done in code inside the tool, not left to the model.** For example, if a paper's ID must be resolved from its title before its card can be read, `get_paper_card` resolves it itself, instead of offering two tools and relying on the model to call them in order. Code always keeps the order; a model only usually does. This doesn't replace `tool_choice`: that controls whether the model acts at all at a step, not the order of steps.

### Registry metadata and errors: first answers (2026-11-10)

* **A side-effect flag goes on each registered tool.** First reader: the loop that executes tool calls. A side-effect call that has already been executed is recorded, and on a replay it is **not executed again**. A tool without side effects (`search`) just runs again, which is harmless. The record stores the call's result, and a skipped call returns **exactly the stored text**: any extra note in it would change the next model call's messages, so that call would miss the LLM cache and the replay would stop following run 1. Whether a call was skipped goes in **per-call metadata** (the tool's trace span and the execution record), never in the text the model reads, the same way `cache_hit` works for LLM calls.
* **Decision (2026-11-16): the record is keyed by run ID + tool name + arguments; the value is the result the tool returned.** A fresh run creates a new run ID (a random UUID) and saves it with the run; a replay loads that ID instead of making one. How I got there, because each simpler key failed a concrete case:
  * *Name + arguments alone:* a new run next week that sends the same digest finds last week's row, so no digest is written and nothing shows the error. (`send_digest` writes the digest to an `outbox/` folder rather than emailing it; the reasoning is the same, since a replay would write a duplicate.)
  * *An expiry date (TTL):* fails both ways. A second real request inside the window is skipped, and a replay months later, after expiry, sends a three-month-old digest. Time doesn't say whether two calls belong to the same run.
  * *Anything built from the call's content* (name, arguments, description): identical in both runs, so it can't separate them. The ID has to come from the run.
  * *A timestamp read at call time:* a replay reads a new time and executes again. The time must be read once when the run starts and saved, and then it is just a run ID; a UUID avoids two runs that start in the same second sharing one.
  * *The call's position in the run:* considered and dropped. A faithful replay keeps the positions anyway, and a replay that drifts (one LLM call missed the cache, so the model added a step) would shift the position, find no row and **send again**: the one failure the record exists to prevent. Two different calls in one run already differ in their arguments; two identical calls in one run share a key, so the second is skipped, which is what I want.
  * Same idea as an **idempotency key** in payment APIs: "same call" means "same ID", not "same arguments".
* **Decision (2026-11-16): a separate per-tool duplicate rule lives in the registry.** Replay safety and "what this tool may do in live use" are different problems. A tool can declare its own window; `send_digest`: at most once per recipient per calendar day, using the date when the call happens in a live run. `search` declares none.
* **Decision (2026-11-16): a tool call gets the smaller of two time limits.** The tool's own limit is in the registry ("this kind of call is broken if it takes longer"), because it depends on the tool: searching HotpotQA's 10 paragraphs is not searching the whole library. The run's remaining budget belongs to the agent loop and shrinks each step. The budget alone isn't enough: with 100 s left, a hung `search_library` would eat the whole question's budget instead of failing fast and letting the model retry or move on.
* **Decision (2026-11-16): when too little budget is left, the loop calls no tool and goes straight to answering.** Threshold still open (A5).
* **Decision (2026-11-16): no permission scope for now.** The system runs on my own computer for one user, so there's nobody to keep apart. Revisit if it ever serves several users, and when `python_exec` arrives (what a tool may touch on this machine is a scope question even with one user).
* **Decision (2026-11-16): native tool calling only; no prompt-based mode for now.** Native is what production systems use when the model and server support it. Checked what "native" is underneath: Qwen3's chat template in Ollama pastes the tool JSON into the system prompt inside `<tools></tools>` and instructs the model to answer with `<tool_call>{"name": ..., "arguments": ...}</tool_call>`; Ollama parses those tags into `tool_calls`. So native calling *is* prompt-based calling, with a prompt format the model was trained on and a parser Ollama maintains. That also explains three earlier findings: descriptions change replies (they're in the system prompt), tool order matters (definitions are pasted in sequence), and `tool_choice` is ignored (the template has no place for it). This narrows the lean scope in §1: `calling_modes` becomes native plus structured errors, and BFCL is run in native mode only.
* **Decision (2026-11-16, superseded the same day when BFCL was dropped; kept for the reasoning): BFCL gets a dev/test split.** All tuning (tool descriptions, thinking on/off, slot choice) happens on dev; test is run once per frozen config, as with QASPER. **Sizes: 200 dev and 600 test, disjoint, each drawn by proportional stratified sampling by category** (seed 42, the method in `evals/make_subsets.py`); the other 440 questions are unused. Why 600: a binomial CI at 75% accuracy is about ±15 points at n = 32 (a category's share of 200), ±6–9 at a category's share of 600, ±5–7 at 1,040. Going from 1,040 to 600 saves an estimated ~25 min per SMALL test run (from the smoke test's ~3.8 s a call, not measured on BFCL) for a couple of points of precision.
* **Decision (2026-11-16): BFCL matching is strict on arguments and types.** An argument the answer key doesn't list fails the call. A value of the wrong type fails it too (`base=10.0` where the key says `10`): the schema says integer, and in the live system the registry's schema check would reject that call anyway. An argument the key marks as omittable (`""` in its list) may be left out; otherwise its value must be one of the listed ones.

* **Decision (2026-11-16): the tools are redesigned as find + read.** Why: `get_paper_card` and `search_library` both take a short text and return papers with IDs, and the models couldn't tell when to use which (SMALL used `search_library` on 17 of 18 named papers). Mapping the use cases (one named paper, papers on a topic, what a paper says inside, comparing papers, verifying a claim later, reading history later, arXiv and citations later, a digest later) showed the real split is **finding papers vs reading inside one**, and that reading was missing: most of my anchor questions ask about content ("which optimizer", "what baseline"), and a card stops at the abstract.

* **A failed call returns an error message to the agent instead of crashing the loop, and the message says what kind of failure it was.** At least two kinds: a wrong or missing argument (the model sent something the tool can't accept), and a failure inside the tool (the arguments were fine but the tool couldn't finish). Format still open.
* **Decision (2026-11-16): errors are structured, so code can read them as well as the model.** Fields, from the hand-written messages below: whose fault it is (bad argument / tool failed), what was wrong, retry this call or not, what to do instead. The tool writes "what was wrong" and "what to do instead", because each tool fails in its own ways and only it knows, for example, what a valid paper ID looks like.
* **Decision (2026-11-16): two layers of errors.** The registry checks every call against the tool's schema before the tool runs and writes those errors itself (missing argument, wrong type, value not in the `enum`): the same check for every tool, with the message generated from the schema. The tool writes only the errors it alone can recognise (no paper with this ID, library unreachable).
* **Measured (2026-11-16): the size of one error in different formats**, Qwen3 tokenizer (taken from the cached Qwen3-Embedding-0.6B, which shares the Qwen3 vocabulary), on message A:

  YAML saves 8 tokens (about 10%) over one-line JSON: small next to a context of thousands of tokens per step. The loop reads the error as a Python object before it becomes text, so the format only affects the model. **Decision (2026-11-16): the model sees the error as one-line JSON**, matching the JSON of the tool definitions and of its own calls.
* **Decision (2026-11-16): `get_paper_card` takes two optional arguments, `paper_id` and `title`, and at least one must be given.** `paper_id` carries the arXiv pattern `YYMM.NNNNN` (optional `vN`); checked 2026-11-16: all 296 library IDs match it. `title` is free text. One argument with a pattern would have rejected every title. **When both are given, `paper_id` wins; if it isn't in the library, the tool falls back to `title`.** Neither is required in the schema, so the model gives an ID only when it has one (for example from a `search_library` result) instead of inventing one to fill a required field. "At least one" is checked in the tool's code (tool-level error), since `anyOf` in tool schemas is poorly supported. **When the ID and the title point to different papers, the ID's card is returned and the mismatch is flagged in the result**, so the model can see where it went wrong.
* **Decision (2026-11-16): `search_library` takes `k`, default 5, at most 10.** 5 is the A3 setting; the cap keeps a large `k` from flooding the context. In the schema as an integer with `maximum: 10` (and `minimum: 1`, my call), so `k=50` is caught by the registry's schema check before the tool runs.
* **Decision (2026-11-16): the model sees every error, except one kind that code retries first: the tool or the service behind it was unreachable at that moment** (connection refused, a timeout reaching it). That is the same rule `chat_with_llm`'s `should_retry` applies to Ollama. If the retries also fail, the model gets it as a tool failure. Everything else (bad arguments, a tool that ran and failed) goes straight to the model, so it can decide what to do.
* **Error messages, written by hand first (2026-11-16)**, to find out what an error has to say:
  * A, bad argument (`get_paper_card(paper_id="transformer paper")`): *"You wrote 'transformer paper' instead of an arXiv ID. Give a valid ID, for example 2401.01234.
