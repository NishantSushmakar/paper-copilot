## 4. Design decisions

### The LLM cache key with tools (2026-11-09)

* **Decision: every offered tool's name, description and parameters schema goes into the cache key.** The rule stays the one the key already follows: everything that can change the reply. The schema is the full JSON the model receives (types, argument descriptions, enums, defaults, `required`).
* **Why the description too:** I first thought the name carried the meaning and the description could stay out. A two-line test showed otherwise. With qwen3:4b, temperature 0, one tool `lookup(query)`, and only the description changed ("Look up facts about any topic." vs "Look up a paper in the user's research library by title. Not for general knowledge."):
  * "Who wrote Hamlet?": a direct answer with A, a different text with B;
  * "What year was the transformer paper published?": both call the tool, with `query` = the whole question (A) vs `'transformer paper'` (B).
  * So the model reads the description as part of the prompt. Leaving it out of the key would make a reworded description silently replay the old replies from the cache, and a description fix would measure as "no change".
* **Output side:** the tool calls a reply makes are stored in the cached value. `LLMResponse` held only text, so a cache hit on a tool-call reply would have lost the calls. It now has `tool_calls` (name, args, id), defaulting to an empty list so older entries still load.
* **Decision (agent's call, 2026-11-10): a call without tools hashes exactly as before.** `tools` and `tool_choice` enter the key only when set, and plain `{"role", "content"}` messages come out of the normalisation unchanged, so the A1–A3 caches stay valid. Also `tool_choice` without tools raises, and a tool result whose call isn't in the conversation raises.
* **Decision: the tool's Python body stays out of the key.** One agent step is two model calls. The first (question + tool definitions → "call search(...)") contains nothing the body produces, so fixing the body can't change its reply, and its cached reply stays valid. The body's effect reaches the model only as the tool result in the *next* call's messages, and messages are already in the key, so that call misses the cache and gets a fresh reply by itself. Putting the body in the key would only discard valid first-call replies on every code change.
* **Found 2026-11-09: turn-2 messages break the key.** From the second agent call on, `messages` holds LangChain objects (`AIMessage` with tool calls, `ToolMessage`), and `json.dumps` raises `TypeError: Object of type HumanMessage is not JSON serializable`. Also, ChatOllama gives every tool call a fresh random id (checked: the same call with the same arguments got two different UUIDs in two runs), so serialising the objects as they are would put a random value in the key, and every call after the first would miss the cache on replay.
* **Decision: a message enters the key as its role, its text content and, for an assistant message, each tool call's name and arguments.** Text alone isn't enough: two runs whose assistant called `search(query="SecAlign")` vs `lookup(title=...)` both have empty assistant text, and "Paris" from the user is not "Paris" returned by a tool.
* **Decision: random tool-call ids are renamed by position before keying.** The id links a tool result to its call, which matters with parallel calls, so it can't just be dropped. In the key, the first call in the conversation becomes call 1, the next call 2, and so on, and each tool result points to the renamed id of its call. The same step run twice gets the same key despite new UUIDs; results that come back in a different order still give a different key, which is right, because the model reads messages in order.
* **Decision: the tool list goes into the key in the order given, not sorted.** Ollama pastes the definitions into the prompt one after another, so `[search, lookup]` and `[lookup, search]` are different prompt text and can give different replies. (`sort_keys=True` sorts keys inside dictionaries but never reorders lists.)
* **Decision: `tool_choice` raises an error on Ollama slots, and goes into the key where the provider honours it.** It's a separate setting, not part of any tool definition, so the description being in the key doesn't cover it. LangChain's `ChatOllama.bind_tools` documents it as "currently ignored as it is not supported by Ollama". A setting that is silently ignored is worse than none: an agent passing `tool_choice="required"` would look forced while the model can still answer in plain text. The OpenAI-compatible path (vLLM, hosted models) supports it.
  * Consequence for A5: "the model must act" or "must end with `final_answer`" can't come from `tool_choice` on Ollama. It has to come from the prompt and the loop's own checks.

### The registry: first principle (2026-11-09)

* **A step that must always happen is done in code inside the tool, not left to the model.** For example, if a paper's ID must be resolved from its title before its card can be read, `get_paper_card` resolves it itself, instead of offering two tools and relying on the model to call them in order. Code always keeps the order; a model only usually does. This doesn't replace `tool_choice`: that controls whether the model acts at all at a step, not the order of steps.
