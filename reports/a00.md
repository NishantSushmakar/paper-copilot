## 3. Memory budget

KV cache per token for Qwen3-8B (36 layers, 8 KV heads, head dim 128, fp16): 2 × 36 × 8 × 128 × 2 bytes ≈ **144 KB/token**. Qwen3-4B has the same layer and head layout, so the same per-token cost.

| Context | KV cache per model |
|---|---|
| 8,192 | ~1.2 GB |
| 32,768 | ~4.7 GB |

That is why I run 8K: at 32K the 8B's KV cache alone would take most of the headroom.

Measured loaded sizes: 8B = 6.2 GB (5.2 GB weights + ~1.0 GB, close to the estimate). With the 8-bit KV cache (`q8_0`) a 4B dropped from 3.8 GB to 3.2 GB, as predicted.

**Finding: both chat models don't stay loaded together.** Ollama unloads one to load the other. The log says why: `gpu_free="8.1 GiB"` but `system_free="1.9 GiB"` — the limit was general system RAM, not GPU memory. The biggest consumers were Firefox tabs (~4.5 GB) and a Docker Desktop memory limit of 13.1 GB. Each swap costs a reload (≈2.5 s for the 4B, ≈4.4 s for the 8B), which matters for the A8 router. Options: group eval calls by model, lower Docker's memory limit, close the browser. TODO: re-test after freeing RAM.

## 4. Throughput

Benchmark: ~512-token prompt, 256 output tokens, 6 runs, run 1 discarded as warm-up, mean of runs 2–6 (`scripts/bench_tps.sh`).

| Model | KV cache | Prefill tok/s | Decode tok/s |
|---|---|---|---|
| `qwen3:8b` | fp16 | 276 | 24.5 |
| `qwen3:8b` | q8_0 + flash attention | 276 | 23.7 |
| `qwen3:4b-q4_K_M` | q8_0 + flash attention | TODO | TODO |

(I first benchmarked plain `qwen3:4b` at ~486 / ~45 tok/s, but that turned out to be a different model; see section 5. Its ratio to the 8B was 1.76× prefill, 1.83× decode — below the 2.08× weight ratio, because both models have 36 layers and per-layer overhead doesn't shrink.)

What I learned measuring this:
* **Prefill is ~10× faster than decode.** Decode reads all weights from memory for every token, so it is memory-bandwidth bound: 150 GB/s ÷ 5.2 GB ≈ 29 tok/s ceiling; I measured 24.5, about 85% of peak (≈127 GB/s effective). Prefill processes hundreds of prompt tokens per pass over the weights, so it is compute bound.
* **Warm-up is real.** The first run's prefill was 32 tok/s against ~270 afterwards, even with the model already loaded — first-time GPU kernel setup for a new batch shape. Decode, already warm, was unaffected.
* **A benchmark artefact I almost reported.** Some runs showed 3,500 tok/s prefill. That is physically impossible here (≈2 × 8B × 504 ≈ 8 TFLOP per prompt against a GPU doing roughly 5–7 TFLOPS caps prefill near 400–450 tok/s). Ollama was reusing KV cache from the previous, nearly identical prompt. Fix: make every sentence of every benchmark prompt unique. Lesson: check numbers against what the hardware can physically do.
* **Prompt layout affects speed.** Ollama reuses KV cache for a shared prompt prefix (`cached_tokens: 20` of 21 on a repeated prompt). Putting the long, stable part (system prompt, paper) first and the question last will make repeated questions about one paper faster.

## 5. Model behaviour that affects every later eval

* **Thinking is expensive.** "Say hi in five words" produced 550 tokens (22 s) with thinking on. Counting the r's in "strawberry": 330–496 tokens and 16–20 s with thinking, 118–176 tokens and 4–6 s without.
* **`think: false` is silently ignored on the OpenAI-compatible `/v1` endpoint.** It belongs to Ollama's native API. On `/v1` the switch is `reasoning_effort: "none"`: 27 tokens instead of 135 for the same prompt. No error either way — unknown parameters are dropped silently.
* **The same tag is not the same model.** Ollama's `qwen3:4b` has the same digest as `qwen3:4b-thinking` (Qwen3-4B-Thinking-2507, 262K context). It cannot turn thinking off: with `reasoning_effort: "none"` it thought anyway and leaked a `</think>` into the answer. `qwen3:4b-q4_K_M` is the original hybrid model (40,960 context, same generation as my 8B) and turns thinking off cleanly (18 tokens). This is why digests go in provenance, not just tags.
* **`max_tokens` counts thinking tokens.** With thinking on and `max_tokens=50`, the model spent all 50 tokens thinking and returned **empty content** with `finish_reason: "length"`. In an eval that looks like a wrong answer, but it is a budget problem. Every eval must record and report the truncation rate.
* **Without a temperature, outputs vary.** Two identical requests returned 226 and 126 completion tokens. (The cause of that run: I had misspelled `temperature`, and Ollama ignored the unknown key.)
* **Thinking doesn't guarantee instruction following.** Asked to "just say thank you", the 8B reasoned its way to "You're welcome!".
* **Possible queueing after timeouts (unverified).** A normal call made right after a timed-out thinking call took 5.2 s instead of ~2 s. Hypothesis: Ollama kept generating the abandoned request and the next one waited behind it. TODO: verify in the server log.

## 6. LLM access layer

### How it evolved
1. **From scratch on `httpx`.** I first wrote the client by hand to learn the API: slot lookup from validated config (`slots.py`, Pydantic with `extra="forbid"`), a typed `LLMResponse`, status checks, retries with exponential backoff and jitter, and an overall deadline. Lessons from that version:
   * **Unknown parameters fail silently** (`temprature` was accepted and ignored).
   * **Report what the server returned, not what you asked for** — read the reasoning field if present instead of trusting the `thinking` flag.
   * **Fail loudly.** A retry loop whose last-attempt check never matched made the function return `None` with no error; an eval would have scored server outages as wrong answers.
   * **httpx's timeout is per operation, not a total deadline**, and retries multiply it.
2. **Switched to LangChain on purpose.** Hand-written HTTP plumbing is not what an AI engineer does at work. The access layer now builds LangChain chat models from my slots (`copilot/infra/models.py`) and keeps the decisions in my code (`copilot/llm/llm_client.py`).

### Which LangChain class
| | `ChatOpenAI` → `/v1` | `ChatOllama` → native API |
|---|---|---|
| Thinking on/off | works | works |
| Thinking text returned | **no** — tokens counted, text dropped | yes (`reasoning_content`) |
| Finish reason key | `finish_reason` | `done_reason` |
| Works with vLLM later | yes | no |

I use `ChatOllama` for Ollama slots (I want the thinking text for debugging and tracing) and keep `ChatOpenAI` for OpenAI-compatible servers like vLLM. On the same question at temperature 0 the two paths behaved differently (one finished thinking in 548 tokens, the other hit a 600-token limit), so the API path is part of what defines a run.

Bug I caught: reading `finish_reason` from `ChatOllama` always gives the default `"unknown"` because its key is `done_reason`. A default value hid the mistake.

### Retry policy
| Failure | Exception | Retry? | Why |
|---|---|---|---|
| Server down / restarting | `httpx.ConnectError` | yes | may be back in seconds |
| Stall / connect timeout | `httpx.TimeoutException` | yes | with streaming this only fires on a stall (below) |
| Bad request / unknown model | `ollama.ResponseError` 400, 404 | **no** | the same request gets the same answer |
| Rate limited / server error / gateway | `ollama.ResponseError` 429, 500, 502, 503, 504 | yes | usually transient; 502/504 matter behind tunnels to notebook GPUs |
| Anything else | | no | fail loudly |

Max 4 attempts, waits starting at 1 s, doubling, capped at 10 s, with jitter (so parallel workers don't retry in lockstep). LangChain's `.with_retry()` retries **every** exception by default — including 404s — so the policy has to be explicit. Measured: bad model fails in 0.1 s with no retries.

### Timeouts and why I don't use a hard deadline
`ChatOllama` streams internally even when I ask for one complete answer. So httpx's read timeout resets on every token: with `request_timeout=2` a call still ran 12 s and finished. In practice `request_timeout` is a **stall detector**, and **`max_tokens` is what bounds call length** (≈ `max_tokens` ÷ 24 seconds on the 8B).

Decision: **no hard total deadline.** Worst case is bounded by `max_tokens`, a 30 s stall timeout and 4 capped retries, which is enough for local eval runs. A hard deadline matters for user-facing latency; I'll revisit it in A11.

### Cache key
The cache makes every table regenerable without a GPU, so its key decides whether a cached answer is *really* the answer to this request. Storage is `diskcache` (a dictionary on disk); the key is the design.

| In the key | Why |
|---|---|
| messages | the prompt itself |
| model tag **+ digest** | a tag is a name, the digest is the weights. My `qwen3:4b` showed one tag can point to a different model. The digest is read from the server at runtime, so a stale value in `models.yaml` can't fool it. |
| API path (`ChatOllama` vs `ChatOpenAI`) | the same question at temperature 0 behaved differently on the two paths |
| context length | changes what the model can see |
| thinking on/off | 4 tokens vs 847 for the same question |
| temperature | 0 is greedy, higher is sampled |
| max_tokens | a 5-token budget returns a truncated answer that must never be served for a 1,000-token request |
| response format | JSON mode changes the output; A2 compares exactly this |
| sample index | A7 asks the same question k times on purpose; without the index all k samples are one cached answer and agreement is always 100% |
| server profile + server version | flash attention and the 8-bit KV cache can shift outputs and can't be read per request, so they get a label in `configs/server.yaml`; the Ollama version is read at runtime |

| Not in the key | Why |
|---|---|
| run ID, timestamp | they don't change the answer, and including them would make every new run miss the cache |
| request timeout, retry policy | they decide *whether* an answer arrives, not *which* answer |

The two easiest to get wrong were the sample index and the response format: leaving either out doesn't crash anything, it just makes two different experiments look identical.

How the key is built: the inputs go into one dict, are serialised as JSON with sorted keys (so dict key order doesn't matter, including inside each message and a schema `response_format`), and hashed with SHA-256. `temperature` is cast to float and the counts to int, because `json.dumps` writes `0` and `0.0` differently. List order is deliberately *not* normalised: the order of messages is part of the conversation.

What a hit returns: the stored response is plain data (a dict, not a pickled object, so adding a field to the response class later doesn't break old entries), rebuilt into the same response type with `cache_hit=True`. A hit keeps the **original call's latency**, so latency columns in re-run tables still describe real generation time.

Measured (isolated test cache, `qwen3:8b`):

| Check | Result |
|---|---|
| first call | miss, 4.52 s (includes model load) |
| identical call | **hit, 0.002 s**, same text |
| temperature 0 → 0.7 | miss |
| temperature `0` → `0.0` | hit (same value, same key) |
| message dict keys reordered | hit |
| `sample_index` 0 → 1 | miss |
| `max_tokens` 20 → 21 | miss |
| after closing and reopening the cache (a restart) | hit |
| hit latency equals original latency | yes |

## 7. QASPER

### The data (v0.3)
| Split | Papers | Questions | Gold answers per question |
|---|---|---|---|
| train | 888 | 2,593 | 1.03 on average (max 2) |
| dev | 281 | 1,005 | 1.76 (max 3) |
| test | 416 | 1,451 | 2.45 (max 6) |

Dev and test questions were answered by several annotators, so every question has a *list* of gold answers. I only look at train and dev while designing; test is used once per final configuration.

### How answer F1 works
* Each gold answer has one of four types: **extractive** (`extractive_spans`, a list of spans copied from the paper), **abstractive** (`free_form_answer`), **yes/no** (`yes_no`) and **unanswerable** (`unanswerable`).
* Prediction and gold are normalised (lowercase, punctuation and articles removed, whitespace collapsed) and compared as bags of tokens: precision, recall, harmonic mean — the same as SQuAD answer F1.
* With several gold answers, the score is the **maximum** over them: matching any annotator well earns credit. More references per question on test means more chances to match, which by itself pushes test scores above dev.
* Yes/no and unanswerable golds become the words "Yes", "No" and "Unanswerable" and get ordinary token F1. **Format matters as much as correctness:** a correct "Yes, the paper uses ImageNet" against gold "Yes" scores only 0.4 (precision 1/4, recall 1/1). Prompts must ask for bare "Yes"/"No"/"Unanswerable".

### Turning raw answers into gold strings
The adapter is the only code that knows QASPER's raw JSON. Each annotator's answer becomes one gold string:

| Raw field filled | Gold text |
|---|---|
| `extractive_spans` | spans joined with `", "` (the comma disappears in normalisation, so joining adds no extra tokens; joining with " and " would have added a token the model must produce) |
| `free_form_answer` | the text as written |
| `yes_no` | "yes" / "no". `yes_no` has three states (`None`, `True`, `False`), so it is checked against `None`: a plain truthiness check would turn every "No" into a missing answer |
| `unanswerable` | "unanswerable" |
| nothing | rejected: an answer with no type is a data error, not an unanswerable gold label |

All 1,764 dev gold answers parse: 962 extractive, 431 abstractive, 208 yes/no, 163 unanswerable. Some gold answers are citation placeholders: the dataset replaces references with tokens like `BIBREF19`, so a gold answer can literally be "BIBREF19, BIBREF20". A closed-book model can never produce that; with the evidence in front of it, it can copy it. Part of the closed-book vs oracle gap is therefore a property of the dataset's format.

### Data quirk: unnamed sections
11 sections have `section_name: null` (10 of 12,450 in train, 1 of 3,796 in dev), always the first section of a paper. Most of their paragraphs are PDF-conversion debris (LaTeX layout codes like `10pt`, `[block]I.1em`, plus title and author lines), but a few hold real text, such as an abstract and one paper's method section with equations. None of their 51 paragraphs is used as gold evidence, so the choice doesn't affect A0 scores.

Decision: keep them, with the section name allowed to be missing (`None`). This keeps the real paragraphs for retrieval. Cost, for A3: anything that displays or chunks by section name must handle `None`.

### Which answer type a question belongs to
26% of dev questions (261 of 1,005) have gold answers of *different* types, e.g. "What language pairs are explored?" got one abstractive and one extractive answer. Reporting F1 by answer type needs one type per question.

Rule: **extractive > abstractive > yes/no > unanswerable** (the highest-priority type among the question's gold answers wins).

Why: a question counts as unanswerable only when *no* annotator found an answer. I first considered putting unanswerable second; that relabelled 51 dev questions and nearly doubled the unanswerable bucket (60 → 111), including "What crowdsourcing platform is used?", where one annotator answered "They did not use any platform, instead they hired undergraduate students" and the other marked it unanswerable. That answer exists in the paper, so the question shouldn't count as unanswerable.

| Rule applied to dev | extractive | abstractive | yes/no | unanswerable |
|---|---|---|---|---|
| question counts | 647 | 172 | 126 | 60 |

### F1 implementation check
`evals/metrics/qasper_f1.py`: normalise (lowercase → strip punctuation → drop whole-word articles → collapse whitespace), token F1 with counted overlap (`Counter` intersection, so a repeated word can only match as many times as it appears in the gold), max over gold answers.

Known quirk I kept on purpose: punctuation is deleted, not replaced by a space, so "state-of-the-art" becomes the single token `stateoftheart` and won't match "state of the art" (3 tokens). This is what SQuAD and the official QASPER evaluator do; keeping it makes my numbers comparable with published results.

Hand-computed checks, all matching the code:

| Prediction | Gold(s) | F1 | What it tests |
|---|---|---|---|
| "the BLEU score" | "BLEU" | 0.667 | article removal, partial overlap (P 0.5, R 1.0) |
| "Yes, the paper uses ImageNet" | "yes" | 0.4 | correct but wordy answers lose points |
| "BLEU and ROUGE" | "BIBREF19, BIBREF20" | 0 | no overlap, no division by zero |
| "..." | "yes" | 0 | empty prediction after normalising |
| "yes" | "." | 0 | empty gold after normalising |
| "..." | "the" | 1.0 | both empty (SQuAD convention) |
| "the cat cat cat" | "cat" | 0.5 | repeats counted once per gold occurrence (P 1/3, R 1) |
| "Unanswerable." | "unanswerable" | 1.0 | case and punctuation only |
| "English and French" | "De-En, En-Fr" / "English, French, German" | 0.667 | max over two golds (0 vs 0.667) |

### Adapter check
`evals/adapters/qasper.py` loads a split into one validated example per question. Dev: 1,005 questions, 1,005 unique question IDs (safe to freeze subsets on), types 647 / 172 / 126 / 60 as above; train: 2,593 questions.

### Frozen subsets
200 dev and 200 test questions, sampled once with seed 42 and committed to `evals/subsets/`.

Sampling is **stratified proportionally by question type**: each type keeps its natural share of the split. Counts are rounded with the largest-remainder method so they always sum to 200, and IDs are sorted before sampling with a dedicated `random.Random(42)`, so the sample depends only on the seed and the set of IDs.

| | extractive | abstractive | yes/no | unanswerable |
|---|---|---|---|---|
| dev split (1,005) | 647 | 172 | 126 | 60 |
| **dev subset (200)** | **129** | **34** | **25** | **12** |
| test split (1,451) | 960 | 207 | 205 | 79 |
| **test subset (200)** | **132** | **29** | **28** | **11** |

Checks: 200 unique IDs per file, all present in their split, and re-running the script reproduces byte-identical files.

Why proportional rather than equal (50 per type): the overall F1 stays an F1 on QASPER's natural mix, comparable with published numbers, with no re-weighting; stratifying still removes the luck of the draw in how many of each type land in the sample.

Limitations I accept:
* **12 unanswerable questions is too few for a tight per-type CI.** The unanswerable row will be wide; A7, which is about abstention, can sample its own larger subset.
* **Questions from the same paper are related** (a misread paper costs several questions), so an i.i.d. bootstrap over questions will make CIs somewhat too narrow.
* **Stratifying test uses test labels** (each question's answer type, not the answers). A mild, common practice, noted here for transparency.

### Harness sanity check with fake systems
Before spending any LLM calls, I validated the scoring path with two systems that need no model. A system is just a function: one `QASPERQuestion` in, one output (a `prediction` string plus an optional `LLMResponse`) out. Both live in `evals/systems/qasper.py` with a registry mapping names to functions.

* **oracle_copy** returns the first gold answer's text. It is the only system allowed to look at gold answers, and it exists purely to test the plumbing.
* **always_unanswerable** returns "unanswerable" for every question.

Results on the dev subset (count of questions with F1 = 1.0):

| | extractive | abstractive | yes/no | unanswerable | total |
|---|---|---|---|---|---|
| oracle_copy | 129/129 | 34/34 | 25/25 | 12/12 | **200/200** |
| always_unanswerable | 4/129 | 5/34 | 5/25 | 12/12 | **26/200** |

oracle_copy at 200/200 confirms the adapter and the metric agree: every gold string matches itself after normalisation.

**The surprise: always_unanswerable gets full credit on 14 answerable questions.** Those questions have several annotators. At least one gave a real answer (which is why my type rule labels the question as answerable), but another said "unanswerable". Since QASPER F1 takes the max over golds, abstaining matches that annotator perfectly. Consequences:

* Abstaining is never fully punished on QASPER: it collects free credit on about 7% (14/188) of answerable dev questions.
* The always-unanswerable baseline scores **0.13 mean F1 on dev** (exactly 26/200: every other question scores 0, with no partial overlap). Per type: unanswerable 1.00, yes/no 0.20, abstractive 0.15, extractive 0.03. Any real system has to clearly beat that floor, not just beat zero.
* When I build abstention in A7, QASPER will flatter an abstention policy slightly. I need to keep this number in mind.

### The harness
`evals/harness.py` runs any registered system over a list of questions. Each question becomes one row in `results.jsonl`, written to disk as soon as it is done, so a crash at question 150 keeps the first 149. A row holds the question's identity (ID, type, system), the outcome (prediction, F1), the LLM details when there was a call (latency in ms, thinking, prompt and completion tokens, finish reason, cache hit) and a failure (exception class and message) when the system raised.

**Error policy: record, score 0, keep going.** If a system raises (timeout after retries, bad output), the run doesn't stop: the row gets an empty prediction, F1 = 0 and the error. I count errors as 0 in the mean rather than leaving them out, because leaving them out rewards failing. A system that answers all 200 questions at 0.40 would "lose" to one that errors on the 50 hardest and scores 0.45 on the rest, when that one really scores 0.45 × 150/200 ≈ 0.34. The summary reports the error count and types next to the mean, so a number that dropped because of errors is visible.

Only the system call sits inside the `try`. My own code (scoring, building the row) is outside it on purpose: a bug there should crash the run loudly, not be recorded as 200 "system failures" scoring 0.00. TODO: scoring is currently still inside the `try`; move it out.

**The summary** gives n, mean F1 overall and per question type (with counts, so the 12 unanswerable questions don't read as a solid number), error count and types, and, over the rows that made an LLM call, the truncation rate (finish reason `length`), cache-hit rate, mean latency and total tokens. When no row made a call (the fake systems), those rates are `None`, not 0.0: "0% truncated" would claim a measurement that never happened.

Checked with the fake systems on dev: oracle_copy 1.00 on all 200 with 0 errors; always_unanswerable 0.13; a deliberately raising system gives F1 0, empty prediction and `TimeoutError` in the failure; running into an existing results file is refused.
