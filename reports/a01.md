## 2. The `Paper` model

### Identity: (source, id, version)

* **The version is its own field, an integer.** It isn't part of the ID string. "Is this an update?" is then a plain comparison (same ID, higher version), all versions of a paper come from one filter, and the idempotency key needs no string parsing. It's an integer so that 10 sorts after 9.
* **The source is part of the identity.** QASPER IDs are arXiv IDs, so the same paper can arrive from both sources. They are different records of the same work: QASPER's text is a fixed snapshot parsed by its authors, mine comes from arXiv HTML or PDF, possibly a later version. Merging them would mix two parses.
* **QASPER papers get version 0, not `None`.** In SQL, `NULL` never equals `NULL`, so a `UNIQUE(source, id, version)` constraint would let every duplicate QASPER event through, which is exactly what the key is meant to stop. 0 can't be confused with a real version because arXiv versions start at 1, and QASPER is frozen, so it never needs a second value.

### The other fields

* **`source`** is a fixed set (`qasper`, `arxiv`), so a typo fails validation instead of creating a third source.
* **Section headings are optional.** QASPER has unnamed sections (the A0 data quirk), and arXiv HTML has text before the first heading. A missing heading is `None` rather than an invented placeholder, and the A3 chunker has to handle it.
* **`fetched_at` must carry a time zone**, and naive datetimes are rejected. Fetch times are stored in UTC, as in the A0 provenance.
* **For QASPER, `fetched_at` is when I downloaded the dataset**, not when I load it. Loading the same file twice should give the same paper. It's a fixed value in `configs/ingest.yaml` (2026-10-20 22:57:37 UTC, the download time of the `.tgz`). I first planned to use the JSON files' modification time, but unpacking the archive kept the authors' March 2022 timestamps, so the files on disk don't record when I fetched them.

* **QASPER has no author data, so `authors` is `None`.** `None` means "unknown". An empty list would claim the paper has no authors. This is safe here, unlike the version, because authors aren't part of any unique key.

**Implemented** in `copilot/ingest/paper.py` (`SectionModel`, `PaperModel`). Toy checks: a valid paper builds; a naive `datetime.now()` is rejected (`timezone_aware`); `source="arxv"` is rejected (`literal_error`). `SectionModel` lives in `copilot/` and is not imported from the QASPER adapter, so the system doesn't depend on its own eval code.

### arXiv: the event model

The arXiv poller doesn't produce papers, it produces **events**: "this paper was published" or "this paper got a new version". I keep events **thin**: they carry what the arXiv API returned (title, abstract, authors, categories, dates, PDF link) and nothing derived. Fetching and parsing the full text happens later, in the handler. If parsing breaks, I still have the raw event and can replay it.

* **Two event types, named after what happened at the source.** v1 is `paper_published`, v2 and later is `paper_updated`. Handlers must not assume they've seen earlier versions, so an update can arrive for a paper the system never ingested.
* **`version` must be greater than 0.** arXiv versions start at 1, and 0 is reserved for QASPER, so a 0 on an arXiv event can only be a bug.
* **`authors` is required and can't be empty.** Unlike QASPER, the arXiv feed always has authors, so a missing or empty list means a broken event.
* **The model rejects contradictory events.** `paper_published` with version 3, or `paper_updated` with version 1, fails validation. I put this check in the model rather than trusting the poller, so malformed events (the replay eval injects 5%) fail before they reach the queue.
* **Three timestamps, all time-zone aware:** `published` (when v1 came out), `updated` (when this version came out) and `polled_at` (when my poller saw it).

**Implemented** in `copilot/ingest/events.py` (`ArxivEventModel`). Toy checks: published+v1 and updated+v2 build; published+v3 and updated+v1 are rejected (`value_error`); version 0 (`greater_than`), source `"qasper"` (`literal_error`), empty authors (`too_short`), naive `polled_at` (`timezone_aware`) and `paper_created` (`literal_error`) are all rejected. Not checked: `updated` earlier than `published` still builds.

### arXiv: the poller

`copilot/ingest/arxiv_source.py` asks the arXiv API for `cat:cs.CL` sorted by `lastUpdatedDate`, newest first, 100 results per page, with at least 3 s between requests (arXiv's terms; the config refuses anything lower). I sort by last update rather than submission date because the product cares about new *versions* too: a v2 means the card and the index entries for that paper are stale.

* **Fetching and retrying are separate.** `fetch_page` makes exactly one request and raises on any failure. A wrapper decides whether to try again. That keeps the single request easy to test, and keeps every wait in one place, so the 3 s limit can't be broken by accident.
* **Retry only what waiting can fix.** The question I asked for each error: *will waiting change the answer?*

  | kind | codes | action |
  |---|---|---|
  | transient | 429, 500, 502, 503, timeouts, dropped connections | wait 5 s (fixed), retry, give up after 3 requests in total |
  | permanent | 400, 404 and anything else | raise immediately |

  429 is the interesting case: it's a 4xx, but it means "slow down", so waiting is exactly the fix. The rule isn't "4xx permanent, 5xx transient". `Retry-After` headers are not honoured yet.
* **One bad entry doesn't kill a poll.** Entries that fail validation are skipped and counted, not raised.
* **Raw input is kept.** Every XML page is saved next to the events file, so the parser can be re-run offline, and a poll refuses to write into an existing events file.
* **One event per paper version.** Within one poll, arXiv lists each paper once, at its latest version. Across polls, the same paper produces more events (v1, later v2), the same (id, version) can arrive twice (duplicates), and versions can be skipped entirely (v2 and v3 both between two polls, and I only see v3).

## 4. The queue: design (decided 2026-10-29, not built yet)

I designed the queue by following one event through its life, failures included, before writing any SQL.

**States.** One `status` column whose value says what should happen to the row next: `pending` (waiting for a worker), `processing` (a worker has claimed it), `done` (the paper is stored). My first attempt named the states after what the data looked like (`raw_event`, `preprocessed_event`, `PaperModelEvent`). That fails at the crucial question "is this event being worked on *right now*, or finished?", which is what crash recovery depends on.

**Duplicates.** (source, id, version) is the primary key, and a duplicate insert is ignored (`ON CONFLICT DO NOTHING`) and counted. It must change *nothing*: setting a `done` row back to `pending` would reprocess the paper, which is exactly what the key is meant to prevent. The database enforces this, not a Python "check, then insert". Two workers can both check, both see nothing, and both insert. The constraint makes the check and the insert one step.

**Temporary failures.** The row goes back to `pending` with the attempt count increased, a "not before" time set by backoff with jitter, and the last error saved. Jitter matters because when arXiv goes down, every in-flight event fails at the same moment. Without jitter they'd all retry at the same moment too.

**Permanent failures.** On the third failed attempt, or for a malformed event, the event moves to a **dead-letter table** with the reason. It's moved, not deleted, so a replay command can put it back once the bug is fixed.

**Crashes.** When a worker claims an event, it records the time (a *lease*). An event still `processing` long after its claim time is assumed abandoned and goes back to `pending`. That counts as a failed attempt, so a paper that crashes the worker every time ends up dead-lettered instead of looping forever. The lease limit is **arbitrary for now** (5 minutes, in config), chosen generously, because declaring a live worker dead (double processing) costs more than recovering slowly from a real crash. TODO: replace it with a value based on measured parse times.

**At-least-once, so idempotent handlers.** If a slow worker's lease expires, two workers can process the same version. The queue can't prevent that. So storing a paper is an upsert on (source, id, version): two writes of the same version leave one row.

**Versions: keep only the latest, decided by version number.** When v2 is stored, v1 goes. "Latest" means the highest version number, not the last to arrive: events can come out of order, and a late v2 must not replace a stored v3. Open consequence for A3: an answer that cited v1 now points at text that no longer exists.

**Dead events stay in the queue.** My first plan was to *move* a dead-lettered event out of the queue. Following one scenario through showed the hole: paper X v2 has an unparseable PDF and is dead-lettered, its queue row is deleted, and tomorrow's overlapping poll delivers X v2 again. The key is gone, so it's accepted as new and fails all over again, every day. So the queue row stays, with a fourth status, `dead`. The queue answers "have we seen this key, and where is it?", and the dead-letter table answers "why did it fail?". The dead-letter table can't use (source, id, version) as its key anyway: malformed events may have no id, and `NULL` never equals `NULL`. It numbers its rows instead.

**Replay** moves an event back: the queue row returns to `pending` with 0 attempts, and the dead-letter row is deleted, in one transaction, so a crash can neither lose the event nor duplicate it. Malformed events (no queue row) are resent through the front door, so there's only one way in.

## 5. The queue: schema and front door (built 2026-10-29)

**Schema** (`copilot/ingest/event_queue.py`): `events`, keyed on (source, id, version), with the raw payload, a status limited by a CHECK to `pending`/`processing`/`done`/`dead`, `attempt_count`, `next_attempt_at`, `arrived_at`, `claimed_at` (the lease), `first_claimed_at` and `last_error`; plus an index on (status, next_attempt_at) for the worker's "what's due?" lookup. `dead_letters` has a row number as its key, key columns that may be empty, the raw payload, a `failure_kind` (`malformed`/`exhausted`/`permanent`), the reason, the attempt count and a time. Both tables are `STRICT`: by default SQLite would happily store the text "abc" in an integer column. Times are ISO text in UTC, so they sort correctly as strings.

**Front door** (`enqueue`): one raw line in, one committed row out, and one of three results.
* **Validate at the door.** The queue only ever holds well-formed events with a real key. Anything the event model rejects goes straight to `dead_letters` as `malformed`, with the key copied only where the values have the right type. Copying `"version": "abc"` into the STRICT integer column would make the dead-letter insert fail too, and the event would vanish.
* **The payload is the raw line**, not the model written back out. A re-serialised copy silently changes things (`Z` becomes `+00:00`, unknown fields get dropped), and replay should resend exactly what arrived.
* **`next_attempt_at` starts equal to `arrived_at`.** I first proposed "arrival + 5 minutes so no other worker picks it up". That would have delayed every new event by 5 minutes, and it mixed up two jobs. Keeping workers apart is what `status` does: a claimed row is `processing`, so no one else picks it up. `next_attempt_at` only moves forward after a failure.
* **One commit per event.** My first instinct was one commit per batch. Both survive the kill test on the fixture, because re-feeding the file is safe with idempotent inserts. A live source can't resend, though: only events that are committed are safe. At this scale the cost of a commit per event is negligible.

**Strict types.** Testing the door showed that `"version": true` was *accepted* as version 1: Pydantic converts `true`, `"1"` and `1.0` to `1` by default. A producer sending those is broken, and the door should say so. Setting `ArxivEventModel` to strict mode fixed it. All 300 fixture events still validate, and all three are now `malformed`.

| check | result |
|---|---|
| fixture, first pass / second pass | 300 enqueued / 300 duplicates |
| new row | `pending`, 0 attempts, `arrived_at == next_attempt_at`, payload identical to the raw line |
| `{broken`, `[1,2]` | malformed, empty key |
| `version: "abc"` / `version: 0` | malformed; id kept, version empty / id and version 0 kept |
| `paper_published` with version 3 | malformed (the model's cross-field check) |
| `version: true`, `"1"`, `1.0` | enqueued as v1 before strict mode; malformed after |

## 6. The worker (built 2026-10-29)

`copilot/ingest/worker.py`. A worker loops: expire stale leases, claim the oldest due event, run a handler, record the outcome. Handlers signal failures by type: `TransientError` (waiting might fix it) or `PermanentError` (it won't). Settings live in `configs/ingest.yaml`.

* **Atomic claim.** "Find a due pending row" and "mark it processing" are one `UPDATE ... RETURNING` statement, so there's no gap in which two workers can both see the row as pending: the same race as "check, then insert" for duplicates.
* **Fencing.** Every finishing update only applies while the row is still *mine*: `processing`, with the `claimed_at` I set. A worker whose lease expired and who finishes late gets `lease_lost`, and its update changes nothing.
* **Backoff:** 5 s, doubling per failed attempt (about 5 s, then about 10 s), each wait scaled by a random factor of ±20%. 3 attempts in total.
* **Unknown errors count as transient.** A bug I didn't anticipate is retried, but still capped at 3 attempts, so it ends up `exhausted` rather than looping.
* **Dead-lettering is one transaction:** the queue row becomes `dead` and the dead-letter row is written, together.
* **`done_at`** was added to the schema when I checked the A1 metrics: throughput needs to know when each event finished.

Tested with fake handlers on the 300-event fixture (fast timings: backoff base 0.01 s, lease 0.2 s):

| test | result |
|---|---|
| every event succeeds | 300 done |
| about 10% fail once, transiently | all retried once (27 to 33 per run), then **300/300 done** |
| one always transient, one permanent | exhausted after 3 attempts / dead-lettered after 1; the other 298 done |
| a worker claims an event and "dies" | lease expires, counted as one failed attempt, retried, done |
| the dead worker finishes late | `lease_lost`; the new owner's result stands |
| 4 worker processes on one database | 300 handled, 300 unique, **0 handled twice** |

## 7. Inspecting and replaying dead letters (built 2026-10-30)

`python -m copilot.ingest.dead_letters inspect | replay`. `inspect` prints a count per kind and one line per dead letter. Replaying gives an event another chance, as if it had just arrived. The policy follows from what each kind needs before a retry can succeed:

| kind | what has to change first | replayed |
|---|---|---|
| `exhausted` (server trouble) | nothing; the server just has to be back | by default: `replay` with no options |
| `permanent` (e.g. a parser crash) | a code fix | only when named: `--kind permanent` |
| `malformed` | a fix to the model or the producer | only when named: `--kind malformed` or `--row N` |

Each replay is one transaction: an `exhausted`/`permanent` event's queue row goes back to `pending` with 0 attempts (`last_error` kept as history), and a `malformed` payload goes back through the front door. Either way, the dead-letter row is deleted. To make that possible, `enqueue` was split into a non-committing `insert_event` plus a thin committing wrapper.

Testing turned up one more thing: **SQLite reuses row numbers.** A plain `INTEGER PRIMARY KEY` hands out "highest + 1", so after replaying rows 4–6, the next two dead letters were numbered 4 and 5 again, and "replay row 4" would mean a different event than it did an hour earlier. `AUTOINCREMENT` fixes that: numbers are never reused.

Tested end to end (fake handlers, fast timings):

| step | result |
|---|---|
| fixture + 2 broken lines + 1 line "wrongly rejected" by an old model | 300 enqueued, 3 malformed |
| worker during an outage: 2 papers always get 503s, 1 crashes the parser | 297 done, 2 exhausted, 1 permanent |
| `replay` (no options) | only the 2 exhausted were requeued → done |
| `replay --kind permanent` after "fixing the parser" | 1 requeued → done |
| `replay --kind malformed` | the wrongly rejected line passed → done; the 2 genuinely broken lines were dead-lettered again (new rows 7 and 8, no reuse) |
| re-feeding the whole fixture afterwards | 300 duplicates, nothing changed |

This covers the second "done when" item in a test setting: a poisoned event ends up in the dead-letter table and can be replayed after fixing it. TODO: show it with a real poisoned event in the replay eval.

## 8. Parsing and the real handler (built 2026-10-30)

`copilot/ingest/parse.py` turns a paper's HTML or PDF into sections, and `copilot/ingest/handler.py` is the real handler: fetch, parse, store as a `PaperModel`. Libraries: `beautifulsoup4` for HTML and `pypdf` for PDF. I chose pypdf over PyMuPDF for its permissive licence. Its plainer, layout-free text is a weaker fallback, which is part of what the HTML-vs-PDF comparison should show.

* **HTML first.** arXiv converts LaTeX to HTML at `arxiv.org/html/{id}v{version}`, with nested `<section>` elements that each have a heading. I keep that nesting as `Parent ::: Child`, like QASPER, strip section numbers, drop footnotes, figures and tables, and write formulas as their LaTeX source instead of MathML's symbol-by-symbol text. The abstract (already in the event) and the references are skipped.
* **PDF only as a fallback**, when there is no HTML (404) or the HTML has no paragraphs. Headings are guessed from patterns ("3.2 Results", "A.1 …", plus a list of named headings), and wrapped lines are rejoined.
* **Failure mapping.** 429/5xx/timeouts → `TransientError` (the worker retries). Other HTTP errors, a missing PDF, an unparseable PDF, or no text at all → `PermanentError`.
* **Storage keeps the highest version.** A `papers` table keyed on (source, id). The upsert only replaces a row when the incoming version is higher, so a duplicate, or a v2 arriving after v3, leaves the table unchanged (`stale`).
* **Politeness and reproducibility.** The 3 s gap applies to these fetches too, kept per process, so only **one real worker** runs at a time. Every download is cached under `data/arxiv/raw/` (including a marker for a 404), so re-runs and the replay eval don't fetch the same paper twice.

* no nesting: "3.1 TASKCURATION" instead of "GEPA-Curator Methodology ::: Task Curation"

**Finding during the first real run: withdrawn papers.** The first dead letters were all "no HTML with text, and the PDF is missing (404)", which is odd for papers arXiv had just listed. The raw XML pages explained it: each of these was a **withdrawal**. When a paper is withdrawn, arXiv posts a new version with no full text, only a comment (e.g. *"This submission is being withdrawn by the authors… Please do not cite this version"*, or *"arXiv admin note: This submission has been withdrawn because it does not meet arXiv's research content quality standards"*). To the poller, that's a perfectly valid `paper_updated` event.
* **Keeping the raw input paid off.** My thin event has no `comment` field. The saved XML pages were the only way to explain these failures.
* **Open question for the product:** a withdrawal is real information. If an earlier version is already in `papers`, it's now something the assistant shouldn't cite, and dead-lettering the event leaves that stale version in place. A better behaviour would be to recognise withdrawals (from the comment, or from the missing full text) and mark the stored paper as withdrawn. Not built in lean A1.

## 9. The replay eval: design (decided 2026-10-30)

`evals/a1_replay.py`, run offline from the raw cache (no arXiv requests): the 300 fixture events plus **20% duplicates** and **5% malformed payloads** (six kinds: truncated JSON, a missing field, version 0, a version as text, event type vs version mismatch, a time without a time zone), shuffled with seed 42. The **real handler** runs behind a switch that fails **10% of calls** transiently. The worker process is **killed with SIGKILL** halfway through and a new one is started.

Metric definitions, and why:
* **Redeliveries vs duplicate processing.** I first wanted "the handler ran twice for the same event" to be *the* duplicate metric. Under at-least-once delivery, though, that is *expected* to be above 0: a worker that dies after storing a paper but before marking the event done gets its event handled again. So I report two numbers:
  * **redeliveries** (handler ran more than once for a key): allowed to be > 0, at-least-once at work
  * **duplicate processing rate** (A1's metric: a paper stored more than once): target 0, idempotency at work

  That split is my answer to "why at-least-once plus idempotency instead of exactly-once?": repeated handling is allowed, a repeated effect is not.
* **Eventual success for transient failures.** With a 10% failure chance per call and 3 attempts, an event dies only if all 3 fail: 0.1³. Once an event has failed once, the chance it ends up exhausted is 1%. So 100% is likely but not guaranteed, and a rare exhausted event is the policy working, not a bug. I report the measured rate next to the expected count of exhausted events.
* **Dead-letter precision = injected malformed rows ÷ all dead-letter rows**, plus **recall** (injected malformed rows found ÷ injected). Withdrawn papers stay in the denominator: they lower precision, and I explain them rather than filter them out.
* **A 10 s lease for the eval** instead of the configured 5 minutes. The kill test checks correctness (nothing lost or duplicated), which doesn't depend on the lease length, so waiting 5 minutes would add nothing.
* **Throughput** = events done ÷ wall time of both worker phases, including backoff and lease waits, so it's throughput *under faults*.

Check on the first 60 fixture events: 0 lost, duplicate processing 0, 6/6 transiently failed events recovered, malformed recall 3/3, precision 0.75 (the one non-malformed dead letter is a withdrawn paper), and the restarted worker shows the killed worker's event coming back through lease expiry. These are not the reported numbers; the full run is below.

**The at-least-once window, demonstrated.** The first random-kill run (before this one, made from uncommitted code) had 0 redeliveries: the kill hit an event *before* its paper was stored, so nothing was handled twice.
